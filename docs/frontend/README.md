# BotDesk web frontend

How the UI in `apps/web` is built. Read this before adding a screen. Decisions here were agreed with the owner; change them by asking first.

## The idea in one picture

```
URL ─► src/app/            routes only: each page renders one feature screen
          │
          ▼
       src/features/       everything about one feature lives in one folder
          │  read data with hooks, change it with actions
          ▼
       src/data/store.ts   the ONLY door to data (hooks + actions), including sign-in
          │  API mode: apps/api, except the screens still mock (see Talking to the API)
          ├──────────────► src/data/api/   typed fetch client for apps/api (only store.ts uses it)
          ▼
       src/data/mock/      fake bots, threads, messages… (deleted when the API covers them)
       src/data/types.ts   the shape of everything (Bot, Thread, Message, Approval…)
```

Screens never know where data comes from. The backend is Python (FastAPI): see [docs/backend](../backend/README.md) and ADR 0003.

## Folders

| Folder | What goes there |
|---|---|
| `src/app/` | Routes. Thin: a page imports a screen from `features/` and renders it. `(app)/` holds signed-in pages inside the app shell; `(auth)/` holds sign-in pages without it. |
| `src/features/auth/` | Sign in, sign up, forgot password: the auth layout, password field, and the redirect for people already signed in. |
| `src/features/shell/` | The frame of the app: auth gate, sidebar (collapses to an icon rail), workspace header (logo tile, org switcher, "+"), user menu (sign out), logo. |
| `src/features/threads/` | A conversation: header, message list, composer, details pane. |
| `src/features/messages/` | The cards inside a message (text, reasoning, work log, computer task, question, routine created, file, handoff, tool call line). |
| `src/features/approvals/` | The approval card (risk, reason, taint warning, preview, expiry, decision line), the Edit form built from the tool's argument schema, the approvals inbox, risk labels. |
| `src/features/bots/` | Bot avatar and status, security levels and the policy table (3 levels × 7 risk classes, ADR 0004), the create-bot screen. |
| `src/features/marketplace/` | Templates you can hire. |
| `src/features/onboarding/` | First-time setup (`/welcome`): the steps, their frame and progress, and the redirect from `/` for a new organization's owner. |
| `src/features/routines/` | The routines page (cards with switch, Run now, Edit, Delete), the create/edit routine form and its schedule picker (presets or a cron line; the demo also has steps). |
| `src/features/apps/` | Connect apps: the server's built-in plugins (API), connections, catalog, connect dialog (demo). |
| `src/features/settings/` | Settings shell, section nav and the sections: profile, organization, appearance (theme, accent presets or a custom colour), models & keys, security, members, usage & budgets, memory. |
| `src/features/command-palette/` | ⌘K / Ctrl+K: jump to a bot, group or page. |
| `src/components/ui/` | shadcn components. Add with `pnpm dlx shadcn@latest add <name>`; don't edit by hand. |
| `src/components/` | App-wide providers (theme, tooltips, toasts). |
| `src/lib/` | Small pure helpers (formatting, @mention parsing, handles, schedules, colour contrast), each with a test. |
| `src/hooks/` | Small React hooks shared by features (current time, remembered state, phone check). |
| `src/data/` | Types, store, mock. |

## Routes

| URL | Screen |
|---|---|
| `/` | Phone: the bot list. Tablet/desktop: opens your most recent chat. The owner of a new organization (no bots yet) goes to `/welcome` instead, until setup is finished or skipped. |
| `/welcome` | First-time setup, outside the app shell (`app/(setup)/`, `features/onboarding/`): name the organization, add an AI key, hire a first bot (Chief recommended), connect Gmail. Progress bars, Skip on every step and "Skip setup". Finish opens the first bot's DM. Only for the owner of an organization with no bots (`lib/onboarding.ts`); members who open it go home, and finishing or skipping is remembered per org in this browser (`botdesk.onboarding.done.<orgId>`). |
| `/chat/[threadId]` | A conversation, DM or group. The details pane opens beside it. An empty DM opens with the bot introducing itself (`threads/dm-welcome.tsx`; not a saved message). |
| `/bots/new` | Create a bot: from scratch or a template, with a live preview. |
| `/marketplace` | Hire a ready-made bot. |
| `/approvals` | Every request waiting for a yes, and past decisions. |
| `/routines` | Repeating jobs: schedule in words + time zone, next run, last result, on/off, Run now, delete. |
| `/routines/new` | Create a routine: a bot, what to do, and when (in your time zone). `/routines/[routineId]/edit` edits one. On the API a "Created a routine" card appears in your DM with the bot. |
| `/apps` | Connected accounts, apps to connect, what each lets bots do and its risk. |
| `/apps/callback` | Where the API's OAuth callback sends the browser (`?result=connected&connector=…` or `?result=error&code=…`): says how connecting went (`lib/connections.ts` maps each code to a message; an unknown code gets the generic one, never shown as is) and links back to Connect apps. After an MCP server's sign-in it also links to that server's Review tools. |
| `/apps/mcp/[serverId]` | Review tools for one MCP server: which tools bots are offered and at what risk, and the diff of changed ones (owners and admins change it; members look). |
| `/settings/<section>` | `profile`, `organization`, `appearance`, `models`, `security`, `members`, `usage`, `memory`. `/settings` opens Profile. The section nav stays in view as you scroll. |
| `/sign-in` | Sign in with email and password. Returns you to `?next=` afterwards. |
| `/sign-up` | Create an account. Follows the server's sign-up mode (`useSignUpMode()`, from `GET /auth/options`): the form when `open`; when `invite-only`, the form only from an invite link (`?next=/invite/<token>`, the token goes with the sign-up and you land in that org), otherwise "Sign-up is by invitation…"; when `closed`, a note and no form. /sign-in and the invite page hide "Create an account" when closed. |
| `/forgot-password` | Ask for a reset link (shows a "check your email" message). |
| `/invite/[token]` | Accept an invite link from Settings → Members. Signed out, it offers sign in / create account and comes back. |

## Talking to the API

One setting picks where data comes from: `NEXT_PUBLIC_API_URL` in `apps/web/.env.local` (copy `.env.example`).

```bash
NEXT_PUBLIC_API_URL=http://localhost:8000   # run the API with `pnpm dev:api`
```

| Chats | Real. The chat list is `GET /threads`; every bot gets a DM, and one you haven't talked to yet has its DM opened (`POST /threads/dm`) when the org loads. DM titles follow the bot's current name. Opening a chat first asks for its active runs (`GET /threads/{id}/runs?active=true`), then follows its event stream from the `replayFrom` that returns (`GET /threads/{id}/events?after=…`, an `EventSource` with credentials) and loads its newest 50 messages ("Show earlier messages" pages back with `before`), so nothing between the two is missed. `replayFrom` is just before the unfinished runs' first events, so a reply opened midway shows all its words and tool lines, not only the ones after you opened it. Replayed events are safe to apply twice: each run remembers the newest event id applied (`lastEventId` on the run), and a `message_delta` at or below it, or for a reply that's saved, is skipped. That list sets the chat's runs (`withActiveRuns` in `api/run-events.ts`): a running bot shows typing dots and "Thinking…", a paused one "Waiting for approval", a stuck one the needs-attention notice with Stop. Runs not in the list have ended, except one you just sent and one heard on the stream after the list's `lastEventId` (it started while the chat loaded); a run the stream already knows is left to the stream. Messages already in the store that the page lacks are kept if they're a reply still being written (a stand-in or a run's words) or newer than the page's oldest message. If the list fails, the stream starts from now. Your message shows at once, then `POST /messages` saves it; the bot's reply streams in: typing dots on `run_started`, words on `message_delta`, the saved reply on `message_saved`, and an inline error on `run_failed`. While a bot replies, Send becomes Stop (`POST /runs/{id}/cancel`). How events change the chat is the pure `api/run-events.ts`. "New group" in the sidebar's New menu starts a group (`POST /threads/groups`) with the bots and people you tick, then opens it. **Unread counts:** each chat's badge is the API's `unread`. The chat on screen in a visible tab is read: `actions.viewThread` (from `ThreadScreen`) calls `POST /threads/{id}/read` on open (a chat opened in a background tab waits until you look), when the tab becomes visible again, and for each new message that arrives while you look at it. The badge shows up to 99 (then "99+") and reads as "N unread messages". A new message from someone else heard on a stream for a chat you aren't looking at (another chat still loading, or a hidden tab) adds one, once, however often it's replayed; the rest come from `actions.refreshChats` (`GET /threads`), which `shell/use-chat-list-polling.ts` runs every 20 s while the tab is visible and on coming back to it (only open chats have a stream). It also brings in groups you were added to and drops ones you were removed from. A list can be a moment old when it lands, so it never undoes what happened meanwhile: a chat started while it was on its way stays, a chat that left your list since (you left a group, a bot and its DM were removed, a removal heard live) stays gone, a chat you read since stays read, and a newer message heard on a stream keeps its preview. (Read and removal marks are on a counter, not the clock, so two things in the same millisecond still have an order.) **Managing a group:** the details pane (`threads/group-members.tsx`) gives the group's creator, owners and admins (`useCanChangeLead`, the same rule) a pencil to rename it (`threads/rename-group-dialog.tsx`, `PATCH /threads/{id}`), "Add people or bots" (`threads/add-to-group-dialog.tsx`, the New group pick list with only those not in it yet, `POST /threads/{id}/participants`) and a Remove button on each member (`threads/remove-member-button.tsx`: shown on hover where there's hover, always on touch screens, with a 44 px tap area; not on yourself; it asks first in an AlertDialog, "Remove Sara Khan from Launch crew?", then `DELETE /threads/{id}/participants/{type}/{id}`). Anyone in the group gets **Leave group** at the foot of the pane (`threads/leave-group-button.tsx`, `actions.leaveGroup`: the same DELETE with your own id); it drops the group from your list and goes home, and when you're the last person its confirm says the group is deleted. A refusal shows in the dialog or as a toast. Everyone with the group open gets the change live (`thread_updated` on its stream; your unread count stays). A change that leaves you out, heard live, drops the group at once and asks for the chat list, which brings it back if you were added back. One replayed as the chat opens (its id at or below the active-runs list's `lastEventId`) may be older than your being added back, so it only asks for the chat list. | Mock threads with fake bot replies; new groups are created in the mock, and renamed, added to, removed from and left there. |
| Bots working together ([ADR 0009](../adr/0009-bots-working-together.md)) | Real. Who replies is the API's call; the web shows it. Runs a bot's @mention started arrive on the stream like any reply (`run_started` with their own `runId`), so they get typing dots and stream in. A system message (`author.type: "system"`) renders as a quiet centred status line (`threads/system-notice.tsx`), e.g. "Stopped a chain of bot replies after 3 hops.". In a DM, the @ list offers the DM's bot first, then every other bot of the org marked "Joins as a guest" (`useMentionOptions` in `composer.tsx`), and a guest's reply shows its name and avatar (`MessageItem`'s `dmBotId`). Groups: New group has a Lead picker once two bots are ticked (default: the first picked, sent as `leadBotId`); the details pane shows the lead (`threads/group-lead.tsx`), and its creator, owners and admins (`useCanChangeLead`) change or clear it (`PUT /threads/{id}/lead`, `actions.setGroupLead`; a refusal shows as a toast). | The same rules, from `lib/mention-routing.ts` (a copy of the API's `services/mention_routing.py`): the lead answers messages with no mention, mentions pull guests into DMs, replies take turns per chat, a fake reply that @mentions a bot in the chat starts its reply one hop on, and past 3 hops the notice shows. Say "relay" in a group to watch the bots hand over until the limit stops them. |
| Handoffs ([ADR 0014](../adr/0014-handoffs-and-tasks.md), [contract](../architecture/handoffs-contract.md)) | Built against the contract (API slices H1–H3 pending). A bot that hands Tasks to teammates saves a message with one `handoff` card per Task (`messages/handoff-part.tsx`): from → to with avatars and @handle, the task, and a status badge (`messages/task-status-badge.tsx`: Queued, Working… with a dot that only pulses when motion is welcome, Done, Failed, Cancelled) in a polite live region. Done folds the result preview open and "View reply" scrolls to and focuses the teammate's reply (`#message-<id>` in the message list); Failed and Cancelled show why, and a budget failure offers the bot's Edit dialog and Usage & budgets. `task_updated` (on the parent run) moves every card with that `taskId` on, but never backwards (`lib/tasks.ts`: queued < working < done/failed/cancelled); the newest state per Task is kept (`taskChanges`), so a card saved or loaded after its update still shows it. `run_waiting_handoff` pauses the run (`waiting_handoff`, with its `taskIds`): the bot says "Waiting on teammates" and the chat shows "Chief is waiting for @sales and @inbox" with Stop (`threads/run-waiting-notice.tsx`). `run_resumed` with `after: "tasks"` starts the final answer as a new message (a missing `after` means an approval). | The Chief demo: ask Chief to "plan the launch" (in its DM, or a group it leads) and it hands Tasks to Sales Outbound and Inbox Manager, waits while each works and replies in turn, then posts one combined answer. Stop cancels the open Tasks. Its words live in `data/mock/chief-demo.ts`. |
| Approvals | Real. A risky tool call pauses the bot's run: `approval_requested` puts the card into the bot's reply (above its text) and the bot's status says "Waiting for approval". Approve / Deny / Edit call `POST /approvals/{id}/decide`; Edit is a form built from the approval's `argsSchema` (`lib/args-form.ts`) and sends `editedArgs`. `approval_decided` updates the card live, `run_resumed` has the bot thinking again. A 409 refetches the approval: if it's decided (elsewhere, or expired) the card shows who decided, and an open Edit form says so ("Sara already denied this, so your changes weren't used"); if it still waits (say, the tool went away) the form stays open with your changes and a toast. A 400 shows the API's field errors in the form. The form leaves out optional fields the bot didn't send unless you fill them in, and keeps numeric enums as numbers. Clearing an optional field the bot sent sends `null` if the schema allows it (`anyOf` with `null`), and otherwise leaves it out, never `""`. Decisions are final in the store: a stale pending copy (a slow poll or list, a replayed event) never undoes one, and a run seen finish is never paused again. Focus: Edit focuses the first field, Cancel returns to Edit, a decision moves focus to the decision line, which sits in an always-mounted polite live region. If someone else decides while your form is open, the form closes, the card says your changes weren't used, and focus moves to the decision line once (only if it was in the form). Tool calls show as a line in the reply ("Used Send email · done") and are saved with it (`tool-call` parts), so a reload shows the same lines. A call that failed after it may have been done (status `unknown`) reads "Tried Send email · may have been done" with why, instead of spinning. `run_needs_attention` shows a notice with Stop (`POST /runs/{id}/cancel`). Opening a chat also loads its approvals, so the cards of a run still going show even before its reply is saved. The Approvals page loads `GET /approvals?status=all` (newest 100) with a bot filter, again on an org switch, and says so with Try again if that fails; the sidebar count polls `?status=pending` every 20 s while the tab is visible (`shell/use-approvals-polling.ts`) and refreshes when a chat hears `approval_requested` / `approval_decided`. | Mock approvals with the same fields (arguments, schema, reason, taint); deciding is instant and the bot confirms in its chat. |

My keys: the demo's built-in providers, none with a key yet. |
| Memory | Real. Settings → Memory picks a bot; the bot details pane has the same list in its Memory tab (`features/memory/bot-memories.tsx`). | The bot's Computer tab | **Still mock.** | Mock. |

- `src/data/api/client.ts` is the fetch wrapper: sends the cookie (`credentials: "include"`) and turns `{detail}` errors (and 422 lists) into an `ApiError` whose message screens show as is.
- `src/data/api/botdesk.ts` lists every route the web app calls; `map.ts` turns API shapes into `types.ts` shapes (including reading zone-less SQLite times as UTC).
- Store actions that can fail return `{ ok: true } | { ok: false, error }` and are async in both modes.
- **Guest mode.** "Explore the demo, no account needed" on /sign-in and /sign-up opens the mock data as Ali in the demo team, in either mode, and never calls the API. `isDemoMode()` is true for guests. A banner on every app page says nothing is saved; "Create an account" signs the guest out and opens /sign-up. It lasts for the browser session (`sessionStorage` `botdesk.guest`), so a reload stays a guest. Entering and leaving both reset the mock store, so real and demo data never mix.
- **No demo data before the API answers.** In API mode the store starts empty (blank org and user stand-ins, the chat list loading), and that same snapshot is what the server renders and the browser hydrates with (`getServerSnapshot`), so there's no hydration mismatch and no flash of demo chats.
- **Tests and e2e always run in mock mode.** Vitest doesn't load `.env.local`, and the Playwright web server sets `NEXT_PUBLIC_API_URL` to empty for its build. Don't set it there.
- Every page under `(app)/` sits behind `AuthGate` (`features/shell/auth-gate.tsx`). If there is no session, it sends you to `/sign-in?next=<where you were>`. Until you're signed in the page is still rendered, but hidden and inert: with Cache Components, Next prerenders every route segment and its dev check (instant navigation) reports any segment a layout leaves out. So screens must not act (redirect, call the API) before `useAuthStatus()` is `"signed-in"`.

## Layout by screen size

| Size | Layout |
|---|---|
| Phone, under 768px | One thing at a time. Bot list is home; a chat is full screen with a back button; details slide up as a sheet. |
| Tablet, 768–1279px | Sidebar + chat. Details slide in from the right. |
| Desktop, 1280px+ | Sidebar + chat + details pane (resizable, can be closed; the app remembers). |

On tablet and desktop the sidebar collapses to an icon rail. The app remembers the choice in `localStorage` (`botdesk.sidebar.open`).

Inside a page, layouts follow the space the page has, not the screen: beside the sidebar a tablet leaves ~540px. Pages that scroll (settings, marketplace) mark their scroll area `@container` and use container variants (`@md:`, `@xl:`, `@3xl:`…) instead of `sm:`/`md:`/`xl:`. Settings also makes the section column a container, so cards and rows size to that column.

Small text buttons and links get a touch-sized hit area without looking bigger: the `tap-target` utility (`globals.css`) adds an invisible box at least 44px square (`[--tap-size:32px]` where neighbours are close). It needs room to overflow, so on an element that clips (`truncate`), grow it with padding and cancel with a negative margin (`-my-2 py-2`) instead.

## Look

Light by default, dark mode from day one (toggle in the user menu). Black and white with one accent, ultramarine `#3B30FF` by default, plus status colours: amber = working, ultramarine = needs your approval, red = error, grey = sleeping. Geist font. Messenger-style chat: your messages on the right in a dark bubble, bot messages on the left in light grey, cards full width under the bot's message. Bot replies are formatted markdown (`features/messages/markdown.tsx`: react-markdown + remark-gfm for lists, tables, task lists, links in a new tab, and code blocks in the UI kit's `CodeBlock` with a copy button and syntax colours from `useHighlightedCode`); raw HTML is never rendered and images show as links, so a reply can't load anything from unknown servers. People's messages show as typed. An @handle starts a word (`lib/mentions.ts`), so the @ in `sara@acme.dev` is not a mention. Under a finished message, Copy and its time show on hover or focus (always on touch). The chat list preview drops markdown marks (`lib/plain-text.ts`).

Members can change the accent in Settings → Appearance: a preset or any custom colour. Text on the accent switches between black and white to stay readable (`src/lib/color.ts`). The choice is saved in this browser (`botdesk.accent`).

## House rules for code

- One component per file, under ~150 lines. If it grows, split it.
- Names come from [GLOSSARY.md](../../GLOSSARY.md): `ApprovalCard`, `Bot`, `Thread`, never synonyms.
- Comments say *why*, not *what*. Plain words, no clever abstractions.
- Server components by default; `"use client"` only for interaction or store reads.
- Every screen handles empty and not-found states.
- Times like "2m ago" are computed in the browser only (`useNow`), so server and browser HTML match.
- The same goes for anything only the browser knows, like the saved theme: render a neutral state until `useMounted()` (`hooks/use-mounted.ts`) is true.
- Logic lives in `src/lib/` or the store, with tests. Every new feature comes with tests in the layers below.

## Tests

Three layers, cheapest first. Add to each when you add a feature.

| Layer | Where | Tools | Run |
|---|---|---|---|
| Logic | `src/lib/*.test.ts`, `src/data/store.test.ts` | Vitest | `pnpm test:web` |
| UI components | `src/features/**/*.test.tsx` | Vitest + Testing Library in jsdom: render, click and type like a user | `pnpm test:web` |
| Whole app | `e2e/*.spec.ts` | Playwright in your installed Chrome, 1440px desktop and phone (Pixel 7) | `pnpm test:e2e` |

- Test setup (browser stubs, fresh mock data after every test) is in `src/test/setup.ts`; render helper in `src/test/render.tsx`.
- Find elements the way a person would: by role and visible text (`getByRole("button", { name: "Approve" })`), not by CSS class.
- E2E tests import `test` from `e2e/fixtures.ts`, which signs in the demo user before the page loads. Auth tests (`auth.desktop.spec.ts`) use Playwright's plain `test`, so they start signed out.
- Files ending in `desktop.spec.ts` run in the desktop project; `phone.spec.ts` runs in the phone project.
- E2E builds the app and serves the production build on :3200, so it never clashes with `pnpm dev:web` on :3000 (change the port with `E2E_PORT`). The first run takes ~1–2 minutes because of the build.

Run everything from the repo root:

```bash
pnpm test:web      # logic + UI component tests, ~10s
pnpm test:e2e      # build, then Playwright on :3200
pnpm check         # typecheck + lint + unit tests, before pushing
```

Inside `apps/web`, `pnpm test:watch` re-runs Vitest as you edit.
